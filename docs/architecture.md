# Architecture and safety boundaries

The Tauri window renders a local compiled React UI with Canvas falling notes. It has no browser filesystem plugin, shell execution capability or remote navigation. Its capabilities grant local events and fullscreen only. The CSP confines scripts/assets to the application. Custom commands expose only specific piano/library operations. No telemetry, update service or web server exists in normal use. Optional MIDI output is limited to the Yamaha Light Guide described below.

`parser.rs` parses MIDI once into the canonical `model.rs` representation, including stable note/part IDs, ticks, tempo/time-signature maps and controllers. SQLite stores that normalized song, metadata and per-arrangement settings. `library.rs` uses SHA-256 content identities, a flushed `.part` copy followed by rename, then a SQLite transaction. Ready is visible only after the managed source and normalized record exist. Startup removes incomplete copies and resolves interrupted delete states; it does not rescan arbitrary source folders. Preserve the data directory and SQLite WAL files as a unit when backing up a running app; preferably close the app first.

`app.rs` serializes persistence and song switches off the UI thread. Its bounded import queue accepts at most 64 files per batch and keeps individual errors. A single-instance plugin handles file-open arguments. The frontend uses the same native library query as the importer and provides direct Open IDs outside filter state.

Named practice versions use an additive SQLite `variants` table and a unified Ready view. Each version points directly to its SHA-256 original and stores independent metadata/settings, removed stable note IDs, per-note pitch overrides, mixed Undo history and a monotonic revision. Schema 3 adds pitch storage without rewriting original rows or discarding schema-2 removal versions/history. Loading filters and overlays the original canonical notes without renumbering IDs or changing note ticks, milliseconds, velocity, duration, tempo maps, controllers or part identities. Empty versions are supported. Copying a version inherits its current removals/pitches with fresh Undo history; every version still points to the same root original.

Removal, pitch moves and Undo commit their full state with a revision-checked atomic update. Only selected-note pitch deltas of −12, −1, +1 and +12 are accepted; one invalid/missing note or a result outside 0–127 rejects the whole operation. Undo stores previous pitches/removal IDs across restarts, bounded to 100 actions and 200,000 individual note changes; oldest actions are discarded when either bound is exceeded. Versioned mixed history and SQL triggers prevent an older editor from overwriting unsupported pitch history. This is forward migration compatibility, not support for editing new versions in an older application.

Create/remove/transpose/Undo commands take the same operations lock as song switching, pause and checkpoint the current session, then load the acknowledged edited snapshot paused. This clears guide/audio notes through the existing native lifecycle. The UI blocks playback and simulated note-on input in edit mode, uses Canvas hit regions for visible notes, and pages the accessible note list in groups of 48, including notes outside the configured keyboard range. Successful pitch moves retain selection; removal, Undo and version switches clear it. SQL triggers prevent deletion of an original with dependent versions, including through an older app. A missing original hides its versions until reimport recovers it. Original rows and managed MIDI bytes are never rewritten by note editing.

The 0.4.0 preview tools plan changes from one saved variant revision without mutating notes, history or settings. A preview contains stable note IDs, current pitches and proposed pitches (or null for removal). The frontend shows the exact changes in pages of 48 and derives an ephemeral After roll; Before shows the saved notes. Neither representation is loaded into the transport for audition. Cancel discards this temporary view. Apply sends the original request and expected revision, not a trusted client-authored change list: the library recomputes it, revalidates it and uses the existing atomic removal/transpose operation to append one Undo batch. App integration takes the operations lock, pauses/checkpoints and reloads the applied version paused. No-op previews do not create history; stale revisions are refused. Schema 3 and history bounds remain unchanged.

After is the default preview view. Its paginated change list replaces the manual selection list until Apply/Cancel; immediate edits, Undo and export are blocked while a preview is active. Tool-option, selection/range, version, navigation and revision changes invalidate it. Applying clears selection after native acknowledgement. These frontend guards complement the server's revision checks; client state is not trusted as permission to persist stale edits.

Chord thinning groups surviving nonpercussion notes by exact `start_tick`, using current overridden pitches. Scope is either all pitched parts jointly or one selected nonpercussion part, independent of playback roles, Solo, hand split and loops. Highest retains one highest-pitch event; bass/highest retains one event at each distinct extreme (one for a unison); limit retains the highest 1–8 note events, including duplicate pitches. Equal-pitch ties use the lower stable ID. It does not cluster nearby onsets, recognize musical melody, retime notes or alter percussion. Whole-song range selection is a frontend selection operation across surviving pitched notes using current pitches below/above the inclusive configured endpoints, independent of list page/filter. Octave preview uses the selected stable IDs with −12/+12; MIDI-range validation remains atomic. Existing immediate pitch buttons retain their existing save behavior.

`exporter.rs` applies a saved version's removals/pitches to the parsed source MIDI while preserving tracks, timing, tempo and source non-note payloads. It pairs note releases using the same FIFO policy as import and supplies canonical releases for retained dangling notes. Re-encoding is bounded, then reparsed and compared against the intended musical notes/timing before any destination write; ambiguous merged same-pitch releases are refused. Reimport assigns fresh source-order IDs. Pressure and other expressive messages remain at their original values/pitches rather than being retargeted. Export is a file operation: preserved SysEx is never routed to the runtime or hardware. Original export remains byte-exact. Both exports create a new destination only and ignore playback speed, roles, split and loops. The UI freezes edit/switch actions around the export dialog without pausing transport solely for export, and shows success only for an acknowledged output path.

`runtime.rs` owns MIDI input and the deterministic `transport.rs` engine on one dedicated thread. It advances using `Instant` deltas, publishes presentation snapshots at about 30 Hz and supplies a bounded queue to `audio.rs`. A separate low-frequency saver writes current settings. An ordered checkpoint prevents a save from using a stale display snapshot. No database or parser runs in the audio callback. The callback uses 128 fixed voices, bounded commands, no locks and no allocation or disk I/O. Overflow resets sound and pauses practice with a visible error.

Musical milliseconds derive from the MIDI tempo map. Wall elapsed time times playback speed advances musical position. Audio frames produce oscillator samples at the actual output sample rate. Canvas frames draw the latest native position with bounded visual interpolation. There is one scheduler; the frontend never schedules musical audio. This is practical desktop scheduling, not sample-accurate timestamped MIDI hardware output. Real USB/key-to-speaker latency remains a physical measurement task.

Light Guide also owns a PC master mute: the runtime sets an atomic flag on startup and acknowledged preference changes, and the audio callback reads it once per buffer to emit zero samples. This covers input monitoring, Listen/accompaniment and clicks, including existing voices. Voices still consume releases and advance their envelopes while muted; disabling guidance restores current audio without replaying queued notes. The listening preference is preserved. The mute neither sends Yamaha volume commands nor changes MIDI input, guide lifecycle or matching.

Only physical input events enter the matcher. Explicitly simulated events remain available for display/audio monitoring but cannot alter matching, held state in the engine, or scores. Playback and guide output never enter the input path internally. MIDI uses separate WinMM input/output connections and audio uses WASAPI. Port names are best-effort identifiers: ambiguous saved names require reselection; device loss pauses and requires explicit reconnect. MIDI monitoring defaults to Yamaha speakers. CC64 sustain affects tone release separately from key matching. Panic, Stop, seek, device changes and shutdown reset voices/controllers.

`light_guide.rs` tracks a deduplicated chord and occurrence identity independently from player input. `Engine::guide_targets` exposes only eligible Practice targets: Wait gates and Timed ±150 ms wall-time windows, filtered by roles, Solo, split and percussion rules. The runtime additionally filters the configured keyboard range. No guide notes are sent during Listen, pause, count-in or without a connected input. Note On is channel 1, velocity 64; Note Off is channel 1, velocity 0. Repeated chord identities send Off before On. The two-second middle-C test pauses practice and works even with the guide toggle off.

Cleanup releases every tracked note on pause, stop, seek, settings/song changes, guide disable, disconnect, Panic and shutdown. Ambiguous failed writes remain tracked; warnings about unreleased outputs survive switching devices. Connecting an output sends 128 channel-1 Note Off messages to clear notes left by a previous interrupted session. Exit waits for worker cleanup and reports a failure. No imported SysEx, configuration/controllers, program changes, playback/Thru or arbitrary MIDI commands are sent. MIDI cannot identify an external echoed message's physical origin: use a direct keyboard connection with other MIDI Thru/echo disabled, and verify no automatic practice advancement with hands off.

Native test mode is enabled only by `--smoke-test <isolated-directory>`. It executes the real UI and commands with generated fixtures and writes results locally. It is dormant in ordinary launches. No testing/debug server listens on a network port.

Visible idle library/disconnected paused practice polls presentation state at 4 Hz and avoids unchanged React updates. Active practice, live input and the device monitor use about 30 Hz. Hidden windows make no status requests. Controls/navigation briefly wake the faster poll; none of these display choices affect native musical timing. Idle audio remains open and has a zero-fill fast path when no voices sound.
