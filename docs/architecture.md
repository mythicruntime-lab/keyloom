# Architecture and safety boundaries

The Tauri window renders a local compiled React UI with Canvas falling notes. It has no browser filesystem plugin, shell execution capability or remote navigation. Its capabilities grant local events and fullscreen only. The CSP confines scripts/assets to the application. Custom commands expose only specific piano/library operations. No telemetry, update service, web server or MIDI output exists in normal use.

`parser.rs` parses MIDI once into the canonical `model.rs` representation, including stable note/part IDs, ticks, tempo/time-signature maps and controllers. SQLite stores that normalized song, metadata and per-arrangement settings. `library.rs` uses SHA-256 content identities, a flushed `.part` copy followed by rename, then a SQLite transaction. Ready is visible only after the managed source and normalized record exist. Startup removes incomplete copies and resolves interrupted delete states; it does not rescan arbitrary source folders. Preserve the data directory and SQLite WAL files as a unit when backing up a running app; preferably close the app first.

`app.rs` serializes persistence and song switches off the UI thread. Its bounded import queue accepts at most 64 files per batch and keeps individual errors. A single-instance plugin handles file-open arguments. The frontend uses the same native library query as the importer and provides direct Open IDs outside filter state.

`runtime.rs` owns MIDI input and the deterministic `transport.rs` engine on one dedicated thread. It advances using `Instant` deltas, publishes presentation snapshots at about 30 Hz and supplies a bounded queue to `audio.rs`. A separate low-frequency saver writes current settings. An ordered checkpoint prevents a save from using a stale display snapshot. No database or parser runs in the audio callback. The callback uses 128 fixed voices, bounded commands, no locks and no allocation or disk I/O. Overflow resets sound and pauses practice with a visible error.

Musical milliseconds derive from the MIDI tempo map. Wall elapsed time times playback speed advances musical position. Audio frames produce oscillator samples at the actual output sample rate. Canvas frames draw the latest native position with bounded visual interpolation. There is one scheduler; the frontend never schedules musical audio. This is practical desktop scheduling, not sample-accurate timestamped MIDI hardware output. Real USB/key-to-speaker latency remains a physical measurement task.

Physical and explicitly simulated player events are distinct from playback. Scheduled notes never enter the matcher. MIDI is read through WinMM and audio output through WASAPI. Port names are best-effort identifiers: ambiguous saved names require reselection; device loss pauses and requires explicit reconnect. MIDI monitoring defaults to Yamaha speakers. CC64 sustain affects tone release separately from key matching. Panic, Stop, seek, device changes and shutdown reset voices/controllers.

Native test mode is enabled only by `--smoke-test <isolated-directory>`. It executes the real UI and commands with generated fixtures and writes results locally. It is dormant in ordinary launches. No testing/debug server listens on a network port.

Visible idle library/disconnected paused practice polls presentation state at 4 Hz and avoids unchanged React updates. Active practice, live input and the device monitor use about 30 Hz. Hidden windows make no status requests. Controls/navigation briefly wake the faster poll; none of these display choices affect native musical timing. Idle audio remains open and has a zero-fill fast path when no voices sound.
